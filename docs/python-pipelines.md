# Python pipelines, lineage and evidence

Author pipeline topology in Python. Use native ZenML @step/@pipeline functions for execution and typed step signatures/materializers for orchestration contracts. Group nested research components into steps only where useful. ZenML is the recommended execution/tracking path; standalone execution remains available offline. Do not duplicate ZenML's artifact DAG, execution status or serialization schemas in a second hand-written registry.

`tools.research_pipeline.Component` and `Pipeline` describe scientific responsibilities and ownership in Python. The CPU example exposes pipeline() and exports manifest() only for frozen run evidence and backward-compatible verification. JSON snapshots are not the authored pipeline definition. Existing JSON projects remain readable; new work uses Python definitions. The compact scientific record retains question, authorized scope, semantic invariants and evidence links, because ZenML does not establish these guarantees.

Run `python -m tools.zenml.pipeline --output NEW_DIRECTORY`. Execution and verification are native ZenML steps with recorded artifact lineage. records/zenml.json identifies pipeline, stack, actual step IDs and artifact references; project runs link to that record. Caching of evidence verification stays disabled. Import and inspect pipeline code before executing it; loading records never imports arbitrary Python.

Comparison is many-to-many. The dashboard groups verified runs by dataset, split, metric and protocol, shows every candidate, all pairwise deltas and a Pareto frontier over available quality/cost measurements. It does not require a fixed reference experiment. Report runtime.tradeoffs (e.g. measured latency_ms and parameters); missing values are unknown. Different scopes/baselines may be compared descriptively, but causal component ablations still require matched controls. A source baseline is an integrity snapshot, not the only scientific comparator.

Visual evidence belongs to each run: sample_id, kind (representative/edge-case), image path/hash, caption, expected and observed behavior. Show inputs with predictions/overlays, normal cases and explicit failure boundaries. Sampling policy and omitted cases belong in the report. `visual_evidence` checks provenance and category coverage; a researcher must inspect the image, and numerical/contract tests still apply. The CPU image example produces actual overlays for representative, empty and border-touching inputs. The offline dashboard embeds hash-checked images without serving research files or rendering raw SVG markup.
